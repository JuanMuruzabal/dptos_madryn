## TR-001: Backend en Go (Opción B)
- **Fecha:** 2026-08-11 (corregida el mismo día antes de implementar código — el borrador inicial del plan había elegido la Opción A por error)
- **Fase:** plan
- **Decisión:** Next.js (frontend, TypeScript) + backend en **Go** (spec §6.1, Opción B). Next/Node aparece solo como herramienta de build del frontend, no como segundo servidor — no se corren dos backends.
- **Alternativas consideradas:** Opción A de la spec — Node/TypeScript (NestJS) como backend, con tipos compartidos entre front y back.
- **Por qué:** Es la opción priorizada por el cliente/equipo del proyecto. Da un binario único, eficiente y barato de hostear (spec §6.1); PostgreSQL sigue siendo la base de datos por su soporte de `daterange` + exclusion constraints (TR-005), independiente del lenguaje del backend.
- **Qué se sacrifica:** Un solo lenguaje en todo el proyecto (TypeScript de punta a punta) y el compartir tipos automáticamente entre `apps/web` y `apps/api` vía `packages/shared-types` — con Go, esos tipos hay que mantenerlos sincronizados a mano (o generarlos desde una spec OpenAPI más adelante) entre los structs de Go y las interfaces TS del frontend. También suma un segundo lenguaje al proyecto, con su propio tooling (Go modules, linters, CI) además del de Node para el frontend.
- **Reversibilidad:** Baja una vez avanzado el backend — cambiar de lenguaje a mitad de proyecto implica reescribir la capa de API.

## TR-006: chi + GORM para el backend Go
- **Fecha:** 2026-08-11
- **Fase:** plan
- **Decisión:** Framework HTTP **chi** (minimalista, compatible con `net/http` estándar) + **GORM** como capa de acceso a datos sobre PostgreSQL.
- **Alternativas consideradas:** Echo o Fiber como framework HTTP (spec §6.1 los menciona como opciones válidas); sqlc+pgx o `database/sql`+pgx a mano como alternativas a GORM.
- **Por qué:** chi tiene la curva de aprendizaje más baja viniendo de un mundo Express/NestJS y máxima compatibilidad con middlewares estándar de Go. GORM acelera el CRUD repetitivo de `apps/api` (alojamientos, experiencias, traslados, reseñas) sin generar código previo, algo valioso para un proyecto con un solo desarrollador.
- **Qué se sacrifica:** El exclusion constraint de reservas (TR-005) y el control de concurrencia de cupos de experiencias (R2 del plan de implementación) no se pueden expresar con la API estándar de GORM — requieren SQL crudo (`db.Exec`/`db.Raw`) igual, así que conviven dos estilos de acceso a datos en el mismo backend. Frente a sqlc, se pierde el chequeo de tipos en tiempo de compilación para las queries generadas.
- **Reversibilidad:** Media — el acceso a datos queda detrás de repositorios/servicios (no se usa GORM directamente desde los handlers), lo que acota el costo de migrar a sqlc más adelante si el raw SQL se vuelve difícil de mantener con GORM.

## TR-002: Reserva + contacto directo + confirmación manual del admin (sin pagos online)
- **Fecha:** 2026-08-11 (refinada el mismo día: el cliente precisó el flujo exacto, reemplazando la idea original de "seña manual" genérica)
- **Fase:** plan
- **Decisión:** El MVP (Fase 1) no cobra nada dentro de la plataforma. Flujo: el cliente reserva un alojamiento (queda `pendiente`) → se contacta directamente con el dueño/administrador fuera del sistema (teléfono/WhatsApp/email) → coordina y hace el pago ahí → el administrador confirma manualmente la reserva desde el panel (pasa a `confirmada`). Esa confirmación es también el disparador de FR-11 (acceso a experiencias/traslados y banner en home, ver TR-007). La integración de cobro con Mercado Pago se difiere y queda como alternativa a evaluar, no como reemplazo obligatorio del contacto directo.
- **Alternativas consideradas:** Integrar Mercado Pago desde el MVP; cobrar una seña automática sin intervención humana.
- **Por qué:** Es el flujo que pidió explícitamente el cliente — preserva el trato humano/personalizado que es el diferenciador del producto (spec §1) en el momento más sensible (el pago), y reduce alcance y complejidad del camino crítico del MVP.
- **Qué se sacrifica:** No hay automatización de cobro ni de reembolsos en el lanzamiento inicial; el admin debe estar disponible para confirmar reservas a tiempo, porque hasta que lo hace el cliente no puede acceder a experiencias/traslados (FR-11) ni ve el banner de confirmación.
- **Reversibilidad:** Alta — la entidad `PAGO` ya está modelada en el ERD (spec §5), así que agregar el proveedor real más adelante no requiere migración de datos, solo la integración.

## TR-007: Acceso a servicios (experiencias/traslados) atado a alojamiento confirmado *vigente*
- **Fecha:** 2026-08-11
- **Fase:** plan
- **Decisión:** Un usuario puede reservar experiencias o traslados solo si tiene al menos una reserva de alojamiento `confirmada` con `fecha_fin >= hoy` (estadía actual o futura). El banner de la home ("¡Tu alojamiento ha sido confirmado! Ver servicios disponibles") usa el mismo criterio. Ver FR-11 y T4.6 en `docs/implementation-plan.md`.
- **Alternativas consideradas:** (a) Cualquier reserva de alojamiento confirmada alguna vez en la historia del usuario, sin importar si ya pasó; (b) exigir que la fecha del servicio elegido se solape específicamente con el rango de una reserva de alojamiento confirmada.
- **Por qué:** Es la lectura más fiel de la intención del cliente ("mientras estás hospedado/vas a hospedarte con nosotros, te armamos el resto de la estadía"), sin la complejidad de UX de exigir una fecha de servicio para poder mostrar el banner genérico de la home (que no depende de qué experiencia se quiera reservar).
- **Qué se sacrifica:** Frente a la opción (a), un huésped recurrente sin una estadía vigente hoy no puede reservar servicios hasta tener una nueva reserva confirmada, aunque haya sido cliente antes. Frente a la opción (b), no se valida que la fecha de la experiencia/traslado caiga dentro de la estadía — un huésped confirmado podría en teoría reservar un traslado para una fecha fuera de su rango de alojamiento; se acepta este hueco por ahora (ver R8/R9 en el plan de implementación) y se puede endurecer más adelante si se vuelve un problema real.
- **Reversibilidad:** Media — la lógica vive en un único endpoint/helper (T4.6) reutilizado por T6.3 y T7.2; migrar a otra definición de "vigente" es un cambio acotado a ese helper, pero cualquier cambio retroactivo de criterio puede sorprender a usuarios que ya se acostumbraron al comportamiento anterior.

## TR-003: Leaflet + OpenStreetMap en vez de Google Maps
- **Fecha:** 2026-08-11
- **Fase:** plan
- **Decisión:** Usar Leaflet + OpenStreetMap para mostrar la ubicación de los alojamientos.
- **Alternativas consideradas:** Google Maps.
- **Por qué:** Gratuito y suficiente para mostrar un marcador simple (spec §6.2), sin costo que escale con el tráfico del sitio.
- **Qué se sacrifica:** Funciones de Google Maps (autocompletado de direcciones más preciso, Street View, mejor cobertura de geocoding en zonas poco mapeadas de la Patagonia) que Leaflet/OSM no ofrece de forma nativa.
- **Reversibilidad:** Media — el componente de mapa queda aislado en el detalle de alojamiento (T2.4 del plan de implementación); migrar a Google Maps más adelante es un cambio acotado a ese componente.

## TR-004: MVP solo en español
- **Fecha:** 2026-08-11
- **Fase:** plan
- **Decisión:** El sitio se construye solo en español para el MVP; soporte bilingüe ES/EN queda como candidato para Fase 3.
- **Alternativas consideradas:** Bilingüe ES/EN desde el MVP.
- **Por qué:** La spec lista "multi-idioma completo" como fuera del MVP (§3) y pide evaluar ES/EN sin definirlo (§10); construir i18n desde el día uno agrega superficie a cada pantalla del MVP sin que esté confirmado que se necesita.
- **Qué se sacrifica:** Turismo internacional (temporada de ballenas) no tiene versión en inglés del sitio hasta Fase 3.
- **Reversibilidad:** Media-Baja — no estructurar los textos con i18n desde el inicio implica trabajo de refactor (extraer strings) si se agrega después; si el cliente confirma que ES/EN es prioritario, conviene adelantarlo antes del Sprint 1.

## TR-005: Exclusion constraint de PostgreSQL para evitar dobles reservas
- **Fecha:** 2026-08-11
- **Fase:** plan
- **Decisión:** La prevención de solapamiento de reservas de alojamiento se implementa como `EXCLUDE USING gist` sobre `(alojamiento_id, rango_fechas)` a nivel de base de datos (spec §5), no como chequeo en la capa de aplicación.
- **Alternativas consideradas:** Validar disponibilidad solo en el backend antes de insertar (lock optimista o chequeo previo en la capa de aplicación).
- **Por qué:** Es la única garantía que no depende de la lógica de la aplicación: dos requests concurrentes a la misma franja de fechas no pueden generar dos reservas confirmadas, sin importar bugs de concurrencia en el backend.
- **Qué se sacrifica:** Requiere la extensión `btree_gist` en Postgres (debe estar disponible en el proveedor gestionado elegido, p. ej. Neon/Supabase) y mensajes de error de constraint violation menos amigables, que el backend debe traducir a un error de negocio legible (ver T3.1 del plan de implementación).
- **Reversibilidad:** Alta — es aditivo a nivel de esquema; se puede quitar sin perder datos, aunque no conviene hacerlo dado el riesgo que mitiga (R1 en el plan de implementación).

## TR-009: Servicio Turístico como entidad separada de Experiencia
- **Fecha:** 2026-08-11
- **Fase:** plan
- **Decisión:** `SERVICIO_TURISTICO`/`SLOT_SERVICIO` es una tabla propia, con el mismo shape de campos que `EXPERIENCIA`/`SLOT` (spec §5), en vez de una sola tabla compartida con un campo `categoria`/`tipo`.
- **Alternativas consideradas:** Una tabla `EXPERIENCIA` única con un enum (`simple`/`compleja`) que distinga ambos casos, reutilizando el mismo CRUD, listado y flujo de reserva para las dos.
- **Por qué:** El cliente pidió explícitamente una **pestaña principal separada** de Experiencias (no un filtro dentro de la misma sección), y aclaró que son conceptualmente distintas para el usuario final (paseos simples vs. excursiones complejas de mayor duración). Modelarlas como entidades separadas evita que un cambio futuro específico de una (p. ej. Servicio Turístico necesita un campo que Experiencias nunca va a usar) fuerce una columna nullable o un chequeo condicional en la tabla compartida.
- **Qué se sacrifica:** Duplicación real de código — CRUD, listado, detalle, reserva con cupos y reseñas se implementan (o al menos se registran como tareas) dos veces, una por módulo (ver Sprint 6 y el nuevo Sprint 8 en `docs/implementation-plan.md`). Mitigable extrayendo componentes/servicios genéricos parametrizados por tabla, pero eso es una decisión de implementación, no de modelo de datos.
- **Reversibilidad:** Media — fusionar ambas tablas más adelante (si el cliente cambia de idea) implica una migración de datos real (mover filas de `servicio_turistico`/`slot_servicio` a `experiencia`/`slot` con un campo de categoría nuevo), no solo un cambio de código.

## TR-010: Catálogo de vehículos con asignación seleccionable por reserva + exclusion constraint propio
- **Fecha:** 2026-08-11
- **Fase:** plan
- **Decisión:** El cliente carga su gama de vehículos (`VEHICULO`, spec §5) desde el panel admin, y el usuario **elige un vehículo específico** al reservar un traslado o un servicio turístico. Para evitar que el mismo vehículo quede asignado a dos reservas con horarios solapados, se agrega un segundo exclusion constraint GiST — igual en espíritu al de alojamiento (TR-005) pero sobre `(vehiculo_id, rango_horario)` con `tstzrange` en vez de `daterange`, porque la granularidad es horas dentro de un día, no noches (ver "Nota clave sobre asignación de vehículos" en spec §5).
- **Alternativas consideradas:** (a) Catálogo puramente informativo (el sitio muestra la gama de vehículos como vitrina, pero la reserva no queda atada a uno en particular — el admin asigna a mano después, igual que ya hace con la confirmación de alojamiento); (b) selección de vehículo sin constraint a nivel DB, confiando solo en un chequeo de disponibilidad en el backend antes de guardar la reserva.
- **Por qué:** Es lo que pidió el cliente — quiere que el usuario vea y elija entre la gama según sus necesidades, no que el admin lo resuelva por fuera. Dado que ya existe el precedente arquitectónico de resolver dobles-reservas con `EXCLUDE USING gist` (TR-005) y que el riesgo es el mismo (dos reservas concurrentes compitiendo por el mismo recurso físico), extender el mismo patrón es más consistente y más seguro que un chequeo solo en la app (opción b).
- **Qué se sacrifica:** Frente a la opción (a), suma una tabla nueva (`VEHICULO`), un segundo exclusion constraint, y una decisión de diseño no trivial (`fecha_hora_inicio`/`fecha_hora_fin` + `rango_horario` generado en `RESERVA`, específicamente para las filas de tipo `traslado`/`servicio_turistico`) — más superficie que un catálogo informativo simple. También hay que definir la ventana horaria real que ocupa un traslado (¿el horario del vuelo con qué margen antes/después?), algo que no estaba definido y hay que acordar con el cliente antes de implementar T7 (ver riesgo nuevo en `docs/implementation-plan.md`).
- **Reversibilidad:** Media — si más adelante se simplifica a "catálogo informativo" (opción a), se puede dejar de exigir `vehiculo_id` en la reserva (columna nullable, no rompe nada existente) y quitar el constraint sin perder datos.

## TR-011: Servicio Turístico se reserva con cupos/horarios fijos (mismo mecanismo que Experiencias)
- **Fecha:** 2026-08-11
- **Fase:** plan
- **Decisión:** Servicio Turístico reutiliza el mecanismo de `SLOT`/`cupos_disponibles` de Experiencias (spec §4.3/§4.4), con su propia tabla `SLOT_SERVICIO` (ver TR-009) — no un flujo de consulta/cotización a medida.
- **Alternativas consideradas:** Flujo de "solicitud de cotización": el usuario manda fechas/cantidad de personas/preferencias y el admin arma la propuesta manualmente por fuera del sistema, sin cupos ni horarios fijos modelados.
- **Por qué:** Mantiene consistencia con el resto del sitio (mismo patrón de reserva en las tres categorías reservables — alojamiento, experiencias, servicio turístico) y no introduce un flujo nuevo de "solicitud sin confirmación estructurada" que el panel admin tendría que soportar aparte. También evita reabrir la discusión de qué pasa con el pago/confirmación para una reserva sin fecha ni precio cerrado de antemano.
- **Qué se sacrifica:** Si en la práctica las excursiones complejas del cliente son en realidad a medida (grupos privados, itinerario negociado, precio variable según el grupo) en vez de salidas con horario y cupo fijo publicados de antemano, este modelo no encaja bien y habría que revisar esta decisión con el cliente antes de Sprint 8.
- **Reversibilidad:** Media-Baja — si se confirma que se necesita cotización a medida, es un flujo distinto (sin `SLOT_SERVICIO`, con un estado intermedio tipo "en negociación"), no un ajuste menor sobre lo ya planeado.

## TR-012: Tipografía Vidaloka + IBM Plex Sans/Mono en vez de Fraunces + Figtree
- **Fecha:** 2026-08-11
- **Fase:** build
- **Decisión:** Se reemplazó el sistema tipográfico de T1.1 (Fraunces para display + Figtree para cuerpo/etiquetas) por tres roles distintos: **Vidaloka** (display, un solo peso, usado grande y con moderación — spec de Google Fonts la describe con carácter de afiche de viaje vintage), **IBM Plex Sans** (cuerpo) e **IBM Plex Mono** (utilitaria: toma la clase `.tracked-caps` completa — nav, eyebrows, columnas del footer). Además, se sacó `uppercase`/`font-semibold` de todos los títulos `font-display` salvo el `<h1>` del hero (que se mantiene en mayúsculas trackeadas como el único momento "grito" de la página), y se agregó un motivo recurrente con las coordenadas reales de Puerto Madryn (`42°46′S 65°02′O`) en mono en el hero y el footer.
- **Alternativas consideradas:** Mantener Fraunces + Figtree con solo ajustes de peso/tamaño; otra pareja "serif cálida + sans neutra" del mismo estilo (Playfair Display, Cormorant, Newsreader combinadas con Inter/Work Sans/DM Sans) — se descartó por ser, en conjunto con la paleta arena+terracota del brief, casi exactamente el combo por defecto que un LLM produce para cualquier landing "premium" sin pensar en el rubro (feedback directo del cliente: la tipografía se sentía "como una presentación de Claude").
- **Por qué:** El cliente pidió explícitamente que se sintiera más original. Vidaloka + Plex Sans/Mono no cambian la paleta ya aprobada (`docs/turismo-marcuzzi-diseno-frontend.md`, fuera de alcance de este pedido) pero sí cambian lo que de verdad se nota — un display con ADN de cartel de expedición en vez de serif de libro, y sobre todo las etiquetas/nav en mono (registro de bitácora/carta náutica) en vez de sans trackeada, que es el tic tipográfico más repetido en sitios "boutique" genéricos. Las coordenadas reales conectan el sistema con el contenido real (un guía que conoce esta costa al detalle), no son decoración.
- **Qué se sacrifica:** Vidaloka solo tiene un peso (400) — cualquier futura necesidad de un display "extra bold" para un momento puntual requeriría otro recurso tipográfico (no forzar `font-bold`/`font-semibold` sobre `font-display`, genera negrita sintética del navegador y se ve mal en una serif; ya se sacaron esas clases de todos los usos existentes). Plex Sans/Mono son más "técnicas" que Figtree — encajan con el ángulo de "guía preciso que conoce el lugar", pero son un poco menos "cálidas" que la sans redondeada anterior.
- **Reversibilidad:** Alta — son solo tokens de fuente (`--font-display`/`--font-body`/`--font-mono` en `globals.css` + los `next/font/google` de `layout.tsx`) y la regla `.tracked-caps`; volver atrás o probar otra combinación no toca estructura ni componentes.

## TR-013: Storage de fotos local (disco) en desarrollo, detrás de una interfaz Storage
- **Fecha:** 2026-08-11
- **Fase:** build
- **Decisión:** T2.1 (carga de fotos de alojamiento) necesita un backend de storage ya, pero no hay credenciales de Cloudflare R2/S3 configuradas en este entorno. Se definió `internal/storage.Storage` (una interfaz de un solo método, `Save`) con una única implementación hoy: `LocalStorage`, que guarda los archivos en disco (`UPLOADS_DIR`, default `./uploads`) y los sirve por una ruta estática `/uploads/*` montada en el router. `apps/api/cmd/api/main.go` instancia `LocalStorage` directo — no hay todavía una rama condicional "si hay credenciales de R2 usar eso".
- **Alternativas consideradas:** (a) Bloquear T2.1 hasta tener credenciales reales de R2/S3; (b) guardar las fotos como base64 en la propia fila de `fotos` en Postgres, sin storage de archivos separado.
- **Por qué:** Bloquear todo Sprint 2 esperando una cuenta de Cloudflare (opción a) para un proyecto de un dev no tiene sentido — el resto de T2.1-T2.5 (listado, filtros, detalle, mapa, calendario) no depende de qué backend de storage se use, solo de que `Foto.URL` sea una URL servible. Guardar base64 en la DB (opción b) infla las filas y las respuestas de la API sin necesidad. La interfaz `Storage` de un método hace que escribir el `R2Storage` real más adelante sea un archivo nuevo, no un refactor.
- **Qué se sacrifica:** El filesystem local no es persistente entre despliegues en la mayoría de los proveedores (Railway/Fly.io) — esto es explícitamente **no apto para producción**, solo para desarrollo local. Antes de T5.5 (deploy) hay que escribir la implementación real de R2/S3 y cambiar la instanciación en `main.go`.
- **Reversibilidad:** Alta — es exactamente el punto de la interfaz. Ningún handler de `alojamientos.go` conoce el detalle de dónde se guarda el archivo.
- **Actualización 2026-08-16:** Resuelto — ver TR-041. `R2Storage` ya existe y `main.go` la elige sola si `R2_BUCKET` está seteado; `LocalStorage` sigue siendo el default de desarrollo local (esta entrada sigue vigente para ese caso, sin cambios).

## TR-014: Email transaccional con LogSender en desarrollo, detrás de una interfaz Sender
- **Fecha:** 2026-08-12
- **Fase:** build
- **Decisión:** T3.3 (email de confirmación al crear una reserva) necesita mandar mail ya, pero no hay API key de Resend configurada en este entorno — mismo problema y misma solución que TR-013. `internal/email.Sender` (interfaz de un método, `Send`) con una única implementación hoy: `LogSender`, que imprime el email en el log del servidor en vez de mandarlo. El disparo es síncrono (no en una goroutine aparte) y best-effort: si falla, se loguea pero no tira abajo la respuesta de la reserva — la reserva ya creada es la fuente de verdad, no el email.
- **Alternativas consideradas:** (a) Bloquear T3.1-T3.3 hasta tener una cuenta de Resend real; (b) omitir el envío por completo hasta Sprint 4/5 y dejar el email como TODO suelto en el código.
- **Por qué:** Igual que TR-013 — no tiene sentido frenar un sprint entero por una cuenta de tercero cuando el resto del flujo (crear reserva, historial, reseñas) no depende de qué Sender se use. Frente a la opción (b), tener el `Sender` real desde ahora (aunque no mande nada) obliga a que el contenido del email (asunto, cuerpo, qué datos de la reserva incluye) ya esté escrito y probado — cuando se sume la API key de Resend, el cambio es literalmente una línea en `main.go`.
- **Qué se sacrifica:** En desarrollo no hay forma de ver el email "de verdad" (solo el texto en el log) — no sirve para probar visualmente el HTML de un email real ni para validar que el proveedor de correo no lo marque como spam. Ninguno de esos riesgos es evaluable hasta tener credenciales reales.
- **Reversibilidad:** Alta — mismo argumento que TR-013: la interfaz aísla el detalle, ningún handler de `reservas.go` sabe si el email se mandó de verdad o se logueó.

## TR-015: Reserva pendiente con formulario de contacto + vencimiento automático de 20 minutos
- **Fecha:** 2026-08-12
- **Fase:** build
- **Decisión:** Al reservar (T3.1/T3.2), en vez de crear la reserva directo con solo fechas, se abre un panel/formulario que pide nombre, apellido, DNI, email (precargado desde la cuenta, editable) y teléfono — un snapshot de contacto para ESA reserva puntual, guardado en `reservas.contacto_*` (no en `usuarios`, ver comentario en `db.Reserva`). Ese formulario también deja reconfirmar/corregir las fechas antes de enviar. Una reserva `pendiente` que nadie confirma en **20 minutos** se cancela sola (`internal/reservas.RunExpirer`, barrido en el mismo proceso cada 1 min) — el exclusion constraint (TR-005) no cambió: sigue bloqueando cualquier reserva activa solapada, pendiente incluida.
- **Alternativas consideradas:** Se evaluó (y se descartó, decisión final del cliente) un modelo donde las reservas `pendiente` **no** bloquean el calendario entre sí (solo lo confirmado bloquea) y el vencimiento de 20 min sería solo prolijidad administrativa, no protección de disponibilidad; el cliente prefirió mantener el modelo original donde pendiente sí bloquea, con el timer como mecanismo anti-abuso real (evita que alguien sin intención de pagar deje fechas trabadas indefinidamente).
- **Por qué:** Es lo que pidió el cliente explícitamente. El timer de 20 min resuelve la preocupación de fondo (gente reservando "para molestar" sin pagar nunca) sin necesitar mecanismos más pesados (rate limiting por cuenta/IP, verificación adicional) — pedir DNI + cuenta logueada ya agrega fricción social contra el troleo casual, y el timer limita el daño de cualquiera que igual lo intente.
- **Qué se sacrifica:** Una reserva legítima donde el dueño tarda más de 20 minutos en confirmar (poco realista si el pago real se coordina por WhatsApp/mail fuera de la plataforma, como ya define TR-002) se cancela igual — el cliente puede simplemente volver a reservar, pero es fricción real. El barrido corre en el mismo proceso del backend (no un cron externo); si se escala a más de una instancia corre redundante en cada una, inofensivo pero desprolijo — revisar si eso importa antes de un despliegue multi-instancia.
- **Reversibilidad:** Media — el timer es un valor (`PendienteTTL` en `internal/reservas`) y un `UPDATE` idempotente, fácil de ajustar o desactivar. El formulario de contacto es más costoso de revertir: ya hay datos reales guardados en `contacto_*` que el panel admin (Sprint 4) va a depender para poder buscar reservas.

## TR-018: Banner "esperando confirmación" apilable + cierre persistente por notificación + menú de cuenta con forma de persona

- **Fecha:** 2026-08-13
- **Fase:** build
- **Decisión:** Refina TR-017 con feedback directo del cliente: (1) Vuelve la franja "esperando confirmación" (fase de 2h) como aviso en la página, pero ya no como un solo banner de 3 estados — es una **franja por reserva**, apilada debajo del banner de 5 min (`components/esperando-confirmacion-banner*.tsx`), y cada una es **cerrable de forma independiente**: si el cliente reserva y contacta en dos alojamientos distintos, ve dos franjas, una debajo de la otra. (2) El cierre de cada franja (y de cada ítem del panel 🔔) es una **preferencia local persistente** (`lib/notificaciones-cerradas.ts`, localStorage vía `useSyncExternalStore`, clave `contexto:reservaId[:tipo]`) — cerrar la franja de la página NO la oculta también del panel de notificaciones (son claves distintas a propósito), y una reserva que pasa de "esperando confirmación" a "confirmada" reaparece como novedad porque cambia de clave. (3) En el panel 🔔, "esperando confirmación" ahora se pinta en ámbar (mismo tono que `reserva-estado-badge.tsx` usa para `pendiente`) y "confirmada" dice explícitamente "Se confirmó tu reserva..."; ambos tipos son cerrables ítem por ítem. (4) El pill "Mi perfil" + botón "Salir" sueltos en el header se reemplazan por un **ícono con forma de persona** (`components/account-menu.tsx`) con un dropdown: Mi perfil / Mi cronograma (placeholder nuevo, `app/cronograma/page.tsx`, mismo patrón `ComingSoon` que Experiencias/Servicio Turístico/Traslados) / Cerrar sesión — ya no hay una opción de salir suelta en el header.
- **Alternativas consideradas:** Guardar el estado "cerrado" en el backend (columna nueva en `reservas` o tabla de preferencias) en vez de localStorage; un solo banner con cola/carrusel para "esperando confirmación" en vez de apilar; mantener el pill+botón separados y solo cambiarles el ícono.
- **Por qué:** El cierre de un aviso es una preferencia de "no quiero verlo más EN ESTE navegador", no un cambio real del estado de la reserva — modelarlo en el backend agregaría una tabla/columna nueva y una llamada de red por cada click de cerrar, para un dato que no le importa a nadie más que a esa sesión de navegador. `useSyncExternalStore` en vez de `useEffect`+`useState` para leer localStorage evita el mismatch de hidratación SSR/cliente de raíz (el snapshot del servidor es siempre "nada cerrado"), sin volver al patrón "mounted" que ya se había descartado en `modal.tsx` por el lint `react-hooks/set-state-in-effect`. Apilar en vez de un carrusel evita esconder información: con dos reservas en curso, un carrusel obliga a elegir cuál mostrar primero.
- **Qué se sacrifica:** El estado "cerrado" no viaja entre dispositivos/navegadores (localStorage es local) — si el cliente cierra un aviso en el celular, en la compu lo sigue viendo. Bug real encontrado en esta ronda y corregido antes de terminar: `getServerSnapshot`/`getSnapshot` de `useSyncExternalStore` deben devolver la MISMA referencia entre llamadas cuando no cambió nada — un `[]` literal nuevo en cada invocación disparó "getServerSnapshot should be cached" y tiró abajo el servidor de dev con un loop de renders; se arregló con una constante `SIN_CERRAR` compartida.
- **Reversibilidad:** Alta — todo el mecanismo de cierre vive en un solo módulo aislado (`notificaciones-cerradas.ts`) y componentes nuevos; sacarlo no toca el modelo de datos ni el backend.

## TR-019: Panel de administración (Sprint 4) — bloqueos de fechas reutilizan la tabla `reservas`, y `isAdminCaller` para listar inactivos en un endpoint público

- **Fecha:** 2026-08-12
- **Fase:** build
- **Decisión:** Dos decisiones puntuales del Sprint 4 (T4.1–T4.6): (1) Los **bloqueos manuales de fechas** del admin (T4.3, spec §4.8) no tienen tabla ni exclusion constraint propios — son filas de `reservas` con un flag nuevo `EsBloqueoAdmin=true`, `UsuarioID` = el admin que lo creó, `Estado='confirmada'` (nunca vence, no tiene flujo de contacto/pago). Así heredan gratis el exclusion constraint que ya impide reservas solapadas (TR-005) y el filtro `estado <> 'cancelada'` que ya usan `disponibilidad`/`list` (T2.2/T2.5) — cero cambios en esas consultas. Se filtran explícitamente afuera de `/me/reservas` y del listado admin de reservas de clientes (`GET /reservas`, T4.4). (2) `GET /alojamientos` (listado público) ahora acepta `?incluirInactivos=true`, pero solo lo honra si el caller manda un JWT de administrador válido (`isAdminCaller`, chequeo "peek" que nunca falla la request, solo no habilita nada si no hay token/rol admin) — evita un endpoint aparte solo para que el panel vea también los alojamientos dados de baja.
- **Alternativas consideradas:** (1) Tabla `bloqueos_fecha` separada con su propio `EXCLUDE USING gist` — funciona, pero Postgres no soporta exclusion constraints *entre* dos tablas distintas, así que un bloqueo y una reserva real igual necesitarían una consulta cruzada para no solaparse entre sí (se pierde la garantía "a nivel de base de datos" que es el punto central de TR-005). (2) Para el listado admin de alojamientos: una ruta nueva tipo `GET /admin/alojamientos`, o exigir `requireAuth+requireRole` en el propio `GET /alojamientos` rompiendo su carácter público.
- **Por qué:** Reusar `reservas` para los bloqueos no es un atajo cosmético — es la única forma de que un bloqueo y una reserva real compitan por el mismo exclusion constraint sin escribir a mano la lógica anti-solapamiento que TR-005 existe específicamente para no tener que escribir. El costo (una tabla con dos "tipos" de fila lógicamente distintos) es menor que el riesgo (una segunda ruta de anti-solapamiento con su propia superficie de bugs de concurrencia). Para el listado de alojamientos, un "peek" opcional de auth es más simple que una ruta paralela y no debilita nada: sin token admin válido, el comportamiento es exactamente el de hoy.
- **Qué se sacrifica:** `db.Reserva` ahora representa dos conceptos (reserva de cliente / bloqueo admin) distinguidos por un flag — cualquier código nuevo que toque esa tabla tiene que acordarse de filtrar `es_bloqueo_admin` según corresponda (ya cubierto en `misReservas`, `listAdmin`, `alojamientoVigente`; documentado en el comentario del campo en `models.go` para que no se repita el olvido). `isAdminCaller` decodifica el JWT dos veces en el peor caso (una vez acá, otra si la request también pasa por `requireAuth` en otra ruta) — no es un problema de performance a esta escala, pero es una pequeña duplicación de lógica de auth fuera del middleware estándar.
- **Reversibilidad:** Media para los bloqueos — migrar a una tabla propia más adelante (si se necesitara, p. ej., un tipo de bloqueo que NO deba competir con reservas) implicaría una migración de datos, no solo de código. Alta para `isAdminCaller` — es aditivo, sacarlo no rompe nada del comportamiento público existente.

## TR-032: `pnpm run typecheck:web` corre `next typegen` antes de `tsc` — CI fallaba, local no

- **Fecha:** 2026-08-13
- **Fase:** build
- **Decisión:** El script `typecheck` de `apps/web/package.json` pasa de `tsc --noEmit` a `next typegen && tsc --noEmit`.
- **Alternativas consideradas:** Dejar de usar los tipos ambient `PageProps`/`LayoutProps` de Next 16 en cada `page.tsx`/`layout.tsx` y tipar los props a mano — descartado: son la forma documentada/recomendada de esta versión de Next (ver `apps/web/AGENTS.md`) para tipar rutas dinámicas con seguridad, y volver a tipado manual pierde esa validación.

- **Qué se sacrifica:** Nada relevante — `next typegen` tarda un par de segundos y no requiere red ni el backend disponible (confirmado corriendo el pipeline completo con el backend Go apagado).

Para el shell de alta: mantener una página de alta distinta y separada — descartado, es exactamente lo que el cliente pidió unificar.
- **Por qué:** Pedir coordenadas numéricas a mano es fricción real para un admin sin conocimientos técnicos (pedido textual del cliente: "es muy complejo pedir coordenadas") — escribir una dirección y ver el pin en el mapa es el mismo mental model que ya usan Google Maps/Uber/etc. El pin arrastrable como fallback evita quedar bloqueado si el geocoding de una dirección puntual de Puerto Madryn no es exacto (Nominatim no siempre tiene cobertura fina en ciudades chicas de la Patagonia). Unificar el shell visual de alta/edición reduce a un solo patrón para mantener (banner + tarjeta blanca) en vez de dos.
- **Qué se sacrifica:** El pin no es accesible por teclado (arrastre solo con mouse/touch) — aceptable para una herramienta interna de admin, no público general, mismo criterio pragmático que ya se aplicó en otras partes del panel. Depender de Nominatim en vivo (sin API key, sin SLA) para el momento de creación de un alojamiento es una dependencia externa nueva — si Nominatim está caído o no encuentra la dirección, el fallback es mover el pin a mano (nunca bloquea el alta, solo la vuelve menos cómoda). Sigue existiendo el input `direccion` como texto libre separado de lat/lng — nada obliga a que coincidan exactamente si el admin escribe una dirección y después mueve el pin a otro lado; se acepta porque el texto de dirección es solo informativo en el detalle público, el pin es lo que de verdad posiciona el marcador del mapa.
- **Reversibilidad:** Alta — `LocationPicker` es un componente aislado que solo le entrega `lat`/`lng`/`direccion` al mismo `<form>` de siempre; volver a inputs numéricos manuales es cambiar un componente, no el contrato con el backend.

## TR-035: Crear alojamiento = borrador oculto que abre directo su propia página en modo editor ("la creación es la primera edición")

- **Fecha:** 2026-08-13
- **Fase:** build
- **Decisión:** El botón "Nuevo alojamiento" del panel (T4.19, corrige el enfoque de TR-034) ya no navega a un formulario aparte — dispara `crearAlojamientoBorradorAction`, que crea de una un alojamiento con datos de relleno mínimo válido (nombre "Nuevo alojamiento", capacidad 1, precio 1, coordenadas del centro de Puerto Madryn) y `borrador: true`, y redirige directo a `/alojamiento/{id}?modo=editor` — la misma página real donde después se edita cualquier alojamiento existente. Ahí el admin carga nombre, descripción, precio, ubicación (LocationPicker, TR-034) y fotos, exactamente como si "crear" fuera "la primera edición". Mientras el alojamiento no se publique explícitamente, queda oculto del listado público: `alojamientoRequest` suma un campo `Borrador bool` que el backend solo lee en `create()` (nunca en `update()`) para poner `Activo: false` en vez de `true`. Se agrega un endpoint dedicado `POST /alojamientos/{id}/activar` (simétrico al `DELETE` que da de baja) y un banner "Todavía no publicado" + botón "Publicar" dentro del propio ModoEditor cuando `!alojamiento.activo`.
- **Bug real encontrado y corregido en el camino:** GORM ignora un valor `false` explícito en `Create()` cuando la columna tiene `gorm:"default:true"` (`db.Alojamiento.Activo`) — no distingue "campo no seteado" de "seteado a false" en un `bool` no-puntero, así que el INSERT quedaba con `activo=true` sin importar lo que se pusiera en el struct de Go antes de crear (confirmado con test manual: la respuesta del POST decía `"activo":true` incluso mandando `"borrador":true`). Se resolvió con un `UPDATE` de seguimiento inmediatamente después del `Create()` cuando `Borrador` es true — mismo mecanismo que ya usan `deactivate`/`activate`, que sí funcionan porque nunca pasan por `Create()`. **De paso**, esto también corrigió un bug pre-existente no relacionado: el viejo mecanismo de "reactivar" (reenviar un PUT idéntico, con un comentario que afirmaba que eso alcanzaba para volver a prender `activo`) en los hechos NO tocaba ese campo en ningún lado del handler `update()` — nunca reactivaba nada. El nuevo endpoint `/activar` lo reemplaza de raíz.
- **Alternativas consideradas:** Convertir `Activo` a `*bool` en todo el modelo para que GORM distinga "no seteado" de "false" en cualquier `Create()` futuro — se descartó por ser un cambio invasivo (todo el código que lee/escribe `Activo` como `bool` tendría que manejar el puntero) para resolver un solo caso de uso; el `Update()` de seguimiento es una línea de riesgo acotado. Para el flujo de creación: mantener el formulario de alta aparte (TR-034) — descartado, es exactamente lo que el cliente pidió cambiar ("la creación es la primera edición").
- **Qué se sacrifica:** `create()` ahora hace dos queries cuando `Borrador` es true (INSERT + UPDATE) en vez de una — irrelevante a esta escala. Un borrador abandonado (el admin crea uno y nunca completa/publica) queda como fila `activo=false` para siempre salvo que alguien lo borre a mano desde el panel — mismo comportamiento que ya existía para "dar de baja", no es un caso nuevo a resolver.
- **Reversibilidad:** Alta — `Borrador` es un campo opcional que solo lee `create()`; sacar el flujo de borrador entero (volver a pedir datos antes de crear) no requiere migración de datos, ninguna fila existente depende de haber pasado por este camino.

## TR-036: FotosManager — preview igual a la vista pública, 10 casilleros fijos, reordenar con drag-and-drop

- **Fecha:** 2026-08-14
- **Fase:** build
- **Decisión:** Rediseño de `components/admin/fotos-manager.tsx` (T4.20, pedido del cliente): (1) arriba, una preview grande igual a la que ve un visitante real (`components/alojamiento/gallery.tsx`) — mismo `aspect-[16/10]`, mismo criterio `<video>` vs. `<Image>` según `foto.tipo`. (2) Abajo, una grilla **fija de 10 casilleros** (`TOTAL_ESPACIOS`, pool compartido entre foto y video, no 10 de cada uno): los llenos muestran la miniatura (clickeable para verla en la preview grande, con botón de borrar); los vacíos son un "+" punteado que abre el selector de archivo — subir ya no depende de un botón "Subir foto o video" aparte, cualquier casillero vacío dispara el mismo input oculto y auto-envía el form apenas se elige un archivo (`onChange` → `formRef.current?.requestSubmit()`). (3) Arrastrar un casillero lleno sobre otro reordena — drag-and-drop nativo de HTML5 (`draggable`/`onDragStart`/`onDragOver`/`onDrop`), sin librería nueva. Para sincronizar el estado local con la prop `fotos` tras una subida/borrado real: un `useEffect` con `setState` adentro (primer intento) — lo bloqueó el lint `react-hooks/set-state-in-effect` (mismo problema ya resuelto antes en `notificaciones-cerradas.ts`/`modal.tsx`, TR-018); se resolvió "ajustando estado durante el render" (comparar contra la última prop vista y llamar `setState` en el cuerpo del componente, no en un efecto) en vez de silenciar el lint.

Reforzar el límite de 10 en el backend, no solo en la grilla del frontend, seguía el mismo criterio ya aplicado a los límites de tamaño de archivo (TR-030): la UI puede pintar 10 casilleros, pero solo el backend puede garantizar que nadie lo salte pegándole directo a la API.

Reordenar hace un `PATCH` por reorden completo (un `UPDATE` por foto en el backend, hasta 10 queries) en vez de mover una sola fila — irrelevante a esta escala (como mucho 10 filas, la operación es rarísima comparada con listar/ver).
- **Reversibilidad:** Alta — `FotosManager` es un componente aislado; el endpoint de reordenar es aditivo (no cambia el contrato de subida/borrado existente) y la columna `orden` ya existía desde antes, solo no tenía una forma de reescribirse en lote.

## TR-038: Tests de backend contra Postgres real por transacción, no mocks de DB

- **Fecha:** 2026-08-14
- **Fase:** plan
- **Decisión:** La suite de tests de `apps/api` (T12 en `docs/implementation-plan.md`, iniciativa de pipeline de CI) corre contra un Postgres efímero real — el mismo `docker-compose.yml` ya existente en local, un service container `postgres:16` en CI — con un helper (`internal/testdb`) que migra el esquema una vez y envuelve cada test en una transacción que se revierte al final. Usa una base de datos separada de desarrollo (`turismo_marcuzzi_test`, nunca `turismo_marcuzzi`).
- **Alternativas consideradas:** Mockear la capa de datos con `go-sqlmock` (aislamiento total, sin Postgres) — se descartó porque hay que matchear a mano las queries exactas que GORM genera (Preloads, SQL crudo de `MAX(orden)`, el `clause.OnConflict` de los upserts), algo frágil que se rompe con cualquier cambio de query o de versión de GORM sin que el código real esté roto. Además, el exclusion constraint de reservas (TR-005) y el de vehículos (TR-010) son comportamiento real de Postgres — no hay forma de mockearlos con sentido, así que de cualquier manera iba a hacer falta Postgres real para esa parte; usarlo para toda la suite evita mantener dos estrategias de test en paralelo.
- **Por qué:** Un mock es una segunda fuente de verdad que hay que sincronizar a mano con el comportamiento real de la base — exactamente el tipo de desincronización silenciosa que las exclusion constraints existen para prevenir a nivel de datos. Postgres real por transacción es el patrón estándar en shops Go+GORM, reproducible sin fricción extra: cualquier developer que ya puede correr `pnpm run migrate:api` (requiere Docker, ya documentado en CLAUDE.md) puede correr la suite completa sin instalar nada nuevo.
- **Qué se sacrifica:** Los tests son más lentos que mocks puros en memoria (aunque a esta escala, segundos no minutos) y requieren Docker corriendo para correr localmente — no es un requisito nuevo (ya hacía falta para `apps/api` en general), pero si algún día se quisiera correr la suite sin Docker (p. ej. un entorno CI muy restringido) habría que revisar esta decisión.
- **Reversibilidad:** Media — migrar a mocks más adelante para los casos que no dependan de comportamiento real de Postgres es posible sin reescribir toda la suite, pero los tests de exclusion constraints seguirían necesitando Postgres real de todas formas.

## TR-041: Storage de fotos en producción — Cloudflare R2 real, no el disco local de TR-013

- **Fecha:** 2026-08-16
- **Fase:** build
- **Decisión:** `internal/storage.R2Storage` (API S3-compatible de Cloudflare R2, vía AWS SDK v2 apuntado al endpoint de la cuenta) es el `Storage` real de producción. `cmd/api/main.go` elige R2Storage en vez de LocalStorage automáticamente si `R2_BUCKET` está seteado — sin eso, sigue en disco local (TR-013), así que el flujo de desarrollo/`docker-compose.yml` no cambia.

(b) AWS S3 directo — mismo SDK, pero con costo de egress por cada foto servida (R2 no cobra egress).

Se acepta porque es exactamente el trade-off que ya anticipaba TR-013 ("antes de deploy hay que escribir la implementación real de R2/S3").
- **Reversibilidad:** Alta — el resto del código (handlers HTTP, tests) solo conoce la interfaz `Storage`, nunca `R2Storage` directo; cambiar de proveedor de objeto (S3, otro compatible) implica escribir otra implementación de la interfaz, no tocar nada más.

## TR-042: Deploy en Render con contenedores Docker, no Railway/Fly.io/Vercel (los asumidos originalmente en la spec)

- **Fecha:** 2026-08-16
- **Fase:** build
- **Decisión:** Los tres servicios de producción (Postgres administrado, API Go, frontend Next.js) se despliegan en [Render](https://render.com), no en la combinación Vercel + Railway/Fly.io + Neon/Supabase que la tabla de arquitectura de `docs/implementation-plan.md` §2 tomaba como supuesto inicial. Ambos servicios de aplicación (`apps/api`, `apps/web`) se buildean con los `Dockerfile` ya existentes (TR-033) en vez de los builders nativos de Render — mismas imágenes que corren en local con `docker-compose.yml`, sin una segunda definición de build paralela. La migración corre en el propio arranque del contenedor (`CMD ["/bin/sh", "-c", "/app/migrate && /app/api"]` en `apps/api/Dockerfile`), no vía `preDeployCommand` — esa feature de Render es exclusiva de planes pagos, no disponible en el plan `free` de este servicio (descubierto al aplicar el blueprint por primera vez). Toda la topología (servicios, healthchecks, qué env vars existen) vive versionada en `render.yaml` (Blueprint) en la raíz del repo — los VALORES de los secrets (`JWT_SECRET`, credenciales de R2, contacto real) nunca se commitean, se cargan una sola vez desde el dashboard de Render (`sync: false` en el blueprint, o `generateValue: true` para que Render genere el secreto solo, como con `JWT_SECRET`).
- **Alternativas consideradas:** (a) La combinación original de la spec (Vercel para el front, Railway/Fly.io para el binario Go, Neon/Supabase para Postgres) — tres proveedores distintos para tres piezas, más superficie de configuración y de billing separado. (b) Configurar todo a mano desde el dashboard de Render sin `render.yaml` — más clicks, nada versionado ni reproducible si hay que recrear un servicio.
- **Por qué:** Un solo proveedor para los tres servicios simplifica networking (mismo panel, variables de entorno cruzadas entre servicios) y billing, sin perder nada que el proyecto necesite hoy — Render tiene Postgres administrado con extensiones estándar de Postgres (incluye `btree_gist`, TR-005), Docker nativo (reusa los Dockerfiles ya escritos y verificados con `docker compose up --build`), y Blueprints para Infrastructure-as-Code. El pedido explícito del cliente de manejar los env vars desde la plataforma "por temas de seguridad" es exactamente el modelo `sync: false` de Render — la estructura es código, el secreto no.
- **Qué se sacrifica:** Se abandona la arquitectura multi-proveedor asumida en la spec original (nunca confirmada por el cliente, era un supuesto de este plan — ver nota en `docs/implementation-plan.md` §1) — no hay pérdida real de nada ya construido, ningún código depende de un proveedor específico salvo la config de deploy misma. El plan free de Render duerme los servicios sin tráfico (cold start en el primer request después de inactividad) — aceptable para el volumen de un MVP, a revisar si se vuelve un problema real de UX.
- **Reversibilidad:** Media — migrar de proveedor más adelante implica reescribir `render.yaml` (o el equivalente del nuevo proveedor) y recrear los servicios, pero el código de la aplicación en sí (Dockerfiles, `internal/storage.R2Storage`, `config.go`) no depende de Render específicamente.
- **Actualización 2026-08-17 (deploy gateado por CI):** El auto-deploy nativo de Render (por push a la rama) no llegó a dispararse solo con los primeros pushes a `main` después de crear el Blueprint — los servicios creados vía Blueprint delegan el trigger de deploy al propio Blueprint, no a un toggle por servicio. Se resolvió agregando un job `deploy` a `ci.yml` (`needs: [web, api, test-api, test-web]`, solo en push a `main`) que dispara el **Sync Hook** del Blueprint (sincroniza `api` y `web` de una sola llamada — a diferencia de un Deploy Hook, que es por servicio) vía el secret de repo `RENDER_SYNC_HOOK_URL`. Con esto el deploy queda explícitamente gateado por los 4 jobs de CI, no solo por el hecho de pushear a `main` — pedido explícito del cliente.

- **Fase:** build
- **Decisión:** `site-header.tsx` mide su propia altura renderizada con `ResizeObserver` y la publica como la variable CSS `--header-height` (`document.documentElement.style.setProperty`, default `8rem` en `globals.css` para SSR/antes de hidratar). Las 6 páginas/componentes que reservaban espacio para el header `fixed` (`AuthShell`, `ComingSoon`, `/alojamiento`, `/alojamiento/[id]`, `/perfil` + su `loading.tsx`, `/admin` layout) pasan de `pt-32` (128px fijo) a `pt-[var(--header-height)]`.
- **Alternativas consideradas:** (a) Subir el valor fijo (p. ej. `pt-40`) para dejar más margen — no soluciona el problema de fondo, solo lo empuja: con dos banners apilados envueltos a varias líneas en una pantalla angosta, cualquier número fijo eventualmente se queda corto. (b) Sacar el `position: fixed` del header y volverlo `sticky` o estático — cambio mucho más grande, afecta el efecto de header transparente-sobre-hero de la home (T1.1) y no era necesario para resolver esto puntual.
- **Por qué:** Bug real reportado por el cliente (2026-08-17, "desde el teléfono... cosas que se sobreponen"): el header fijo no mide siempre lo mismo — `bannerSlot` (reserva pendiente/confirmada/esperando confirmación) tiene texto largo con una cuenta regresiva y puede apilar más de un aviso a la vez; en una pantalla angosta ese texto envuelve a 2-4 líneas en vez de 1, así que el header real crece más allá de los 128px que cada página asumía fijo, y el contenido de la página arrancaba tapado detrás. Medir la altura real en vez de adivinarla elimina la clase entera de bugs, no solo el síntoma de hoy — funciona igual sin importar cuántos banners se sumen en el futuro o cuánto envuelva el texto en cualquier ancho de pantalla.
- **Qué se sacrifica:** Una dependencia más de JavaScript en el cliente para algo que antes era CSS puro — sin JS (o durante el primer frame antes de que el `useEffect` corra), el layout usa el default de `8rem`, que es exactamente el valor viejo hardcodeado; en el peor caso (banner inusualmente alto) se ve el mismo bug que existía antes hasta que el `ResizeObserver` corrige la variable, una ventana de tiempo muy chica en la práctica.
- **Reversibilidad:** Alta — es una sola variable CSS y un efecto en un solo componente (`SiteHeader`); volver a paddings fijos por página es un revert directo si hiciera falta.

## TR-044: Deploy Hooks por servicio en vez del Sync Hook único del Blueprint

- **Fecha:** 2026-08-17
- **Fase:** build
- **Decisión:** El job `deploy` de `ci.yml` dispara dos Deploy Hooks separados (`RENDER_DEPLOY_HOOK_API`, `RENDER_DEPLOY_HOOK_WEB`, uno por servicio) en vez del Sync Hook único del Blueprint que se había armado primero (ver TR-042).
- **Alternativas consideradas:** Investigar más a fondo por qué el Sync Hook no forzó un redeploy real de `api` en ese caso puntual, y seguir usándolo. Se descartó por ahora: Render no expone en su dashboard un log del propio Sync (solo se ve el resultado en cada servicio), así que diagnosticarlo a ciegas cuesta más que cambiar a un mecanismo sin esa ambigüedad.
- **Por qué:** Caso real (2026-08-17): varias corridas del job `deploy` dispararon el Sync Hook con éxito (HTTP 2xx, confirmado en los logs de CI) después de pushes que solo tocaban `apps/web`, pero en algún punto `turismo-marcuzzi-api` quedó sirviendo con el storage de fotos roto — la foto subida antes desapareció y las subidas nuevas fallaban. Solo un **Manual Deploy** manual del servicio `api` lo resolvió. La hipótesis: el Sync Hook reconcilia la definición del Blueprint contra `render.yaml`, pero no necesariamente fuerza un rebuild+redeploy completo de un servicio si Render decide que "no hay cambios relevantes" para él — dejando en el aire qué contenedor real queda sirviendo tráfico. Un Deploy Hook por servicio no tiene esa ambigüedad: siempre es un redeploy completo de ese servicio puntual.
- **Qué se sacrifica:** Dos secrets en vez de uno, y si se agrega un tercer servicio a `render.yaml` en el futuro hay que sumar su propio Deploy Hook a mano en `ci.yml` (con el Sync Hook, un servicio nuevo se cubría solo). Trade-off aceptado: confiabilidad del deploy pesa más que ese ahorro de mantenimiento.
- **Reversibilidad:** Alta — es un secret y unas pocas líneas de `ci.yml`; volver al Sync Hook (o probarlo de nuevo si Render aclara su comportamiento) no requiere tocar nada de la app en sí.

## TR-045: Ping periódico (GitHub Actions cron) para que los servicios de Render free no se duerman

- **Fecha:** 2026-08-17
- **Fase:** build
- **Decisión:** Nuevo workflow `.github/workflows/keep-alive.yml` que hace `curl` a `turismo-marcuzzi-api` (`/health`) y `turismo-marcuzzi-web` (`/`) cada 10 minutos (`schedule: cron`), más un `workflow_dispatch` para dispararlo a mano.

Tampoco cubre la base de datos (plan free de Postgres en Render no se "duerme" igual que los servicios web, así que no hace falta pingearla) ni resuelve el borrado automático de esa base a los 30 días (ver el comentario de `plan: free` en `render.yaml`, sigue pendiente subirla a `starter` antes de la primera reserva real).
- **Reversibilidad:** Alta — es un solo archivo de workflow sin secrets ni estado; borrarlo (p. ej. al subir los servicios a un plan pago) no afecta nada más.

## TR-047: CAPTCHA en el registro con Cloudflare Turnstile, verificado server-side, deshabilitado por default vía interfaz nil

- **Fecha:** 2026-08-17
- **Fase:** build
- **Decisión:** `POST /auth/register` exige un `captchaToken` (Cloudflare Turnstile) y lo valida contra la API de verificación de Cloudflare (`internal/turnstile.HTTPVerifier`, implementa la interfaz `turnstile.Verifier`) antes de tocar la base de datos. `authHandler.captcha` es del tipo interfaz, y `nil` significa "sin CAPTCHA configurado" — el chequeo entero se salta si es `nil`, así que los ~10 tests preexistentes de `TestRegister_*` que construyen `authHandler{}` a mano siguen pasando sin tocarlos. En dev/CI/docker-compose, `TurnstileSecretKey`/`NEXT_PUBLIC_TURNSTILE_SITE_KEY` caen por default al par de claves de prueba que Cloudflare documenta públicamente ("siempre aprueba"), así que el registro funciona out-of-the-box sin cuenta real de Cloudflare; producción (Render) requiere setear las claves reales a mano (`sync: false` en `render.yaml`).
- **Alternativas consideradas:** (a) hCaptcha o reCAPTCHA v3 — mismo patrón de integración (site key pública + secret key server-side), pero Turnstile es el que el usuario pidió explícitamente ("Cloudflare Turnstile (recomendado)" tras preguntarle). (b) Validar el CAPTCHA solo en el frontend (bloquear el submit sin token) sin verificación server-side — se descartó de entrada: un CAPTCHA que no se valida en el servidor no previene nada, cualquiera puede pegarle directo a la API saltándose el frontend.
- **Por qué:** El registro es el único endpoint público de escritura sin autenticación previa de este proyecto — el candidato obvio para spam/bots automatizados. Verificarlo server-side (no solo gatear el botón de submit en el cliente) es lo que realmente lo hace efectivo. El default nil-disabled evita que este cambio rompa ningún test ni bloquee el flujo en ambientes donde no se configuró Cloudflare todavía.
- **Qué se sacrifica:** Una dependencia externa más (Cloudflare) en el flujo crítico de alta de usuarios — si el servicio de Turnstile está caído o lento, el registro se ve afectado. Se acepta porque Cloudflare Turnstile es infraestructura de alta disponibilidad y el resto del sitio (imágenes vía R2 — TR-041) ya depende de la misma plataforma.
- **Reversibilidad:** Alta — `turnstile.Verifier` es una interfaz de un solo método; quitar el CAPTCHA es pasar `nil` en `cmd/api/main.go` sin tocar nada más, y cambiar de proveedor es escribir otra implementación de la interfaz.

## TR-050: "Ingresá con Google" — Authorization Code flow (popup) intercambiado en el backend, no ID-token verificado en el cliente

- **Fecha:** 2026-08-18
- **Fase:** build
- **Decisión:** El botón de Google (`google-signin-button.tsx`) usa Google Identity Services en modo **Authorization Code** (`google.accounts.oauth2.initCodeClient`, `ux_mode: "popup"`) en vez del modo más simple de "Sign In With Google" (`google.accounts.id`, que devuelve directamente un ID token firmado, verificable sin necesitar un client secret). El `code` que devuelve el popup viaja a `POST /auth/google` (Server Action → Go), que lo intercambia server-side contra `https://oauth2.googleapis.com/token` (`redirect_uri: "postmessage"`, el valor sentinel que Google documenta para este flujo en modo popup) usando `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, y recién ahí pide los datos de la cuenta a `https://www.googleapis.com/oauth2/v3/userinfo` con el access token obtenido (`internal/googleauth.HTTPExchanger`). El client secret nunca sale del backend.
- **Alternativas consideradas:** El modo ID-token (`google.accounts.id.renderButton`/`prompt()`) es más simple (no necesita client secret, el backend solo verifica la firma del JWT contra las claves públicas de Google) pero se descartó por dos motivos: (a) el pedido explícito del cliente (`docs/prompts-login (1).md`, Prompt 2: "Dejá las credenciales y secretos (client ID, **client secret**, ...) en variables de entorno") asume un client secret real, que el modo ID-token no usa; (b) el botón "Ingresá con Google" de Prompt 1 ya es un botón propio con el estilo del sitio — el modo ID-token empuja hacia el widget/botón que renderiza Google mismo (`renderButton`) para mantener la conformidad de Google con el flujo, mientras que `initCodeClient` deja el trigger (nuestro botón, nuestro estilo) completamente bajo control de React, igual que ya se hace con Turnstile (`turnstile-widget.tsx`, render explícito en vez del div `data-sitekey` de auto-render).
- **Por qué:** Con el flujo de código, el intercambio pasa siempre por un paso server-to-server autenticado con el client secret — un atacante que intercepte el `code` en tránsito no puede canjearlo por nada sin ese secret (a diferencia de un ID token, que ya ES la prueba de identidad final, aunque de todas formas viaja por HTTPS). No es una ganancia de seguridad crítica para este caso puntual, pero es el flujo que el pedido del cliente ya asumía.
- **Qué se sacrifica:** Dos llamadas HTTP server-side en vez de una verificación de firma local (más simple/rápida, sin red) — latencia extra despreciable para un login. Sin un par de credenciales de prueba público (a diferencia de Turnstile, TR-047) — probar este flujo, incluso en desarrollo local, requiere una cuenta real de Google Cloud Console con un OAuth Client ID configurado.
- **Reversibilidad:** Media — migrar al modo ID-token más adelante implica cambiar el componente del botón (`google-signin-button.tsx`) y el handler del backend (`googleauth.Exchange` pasaría a verificar un JWT en vez de intercambiar un code), pero el resto del flujo (find-or-create de `Usuario`, emisión de la sesión) no cambia.

## TR-051: Confirmación de cuenta por email — register ya no devuelve token, login rechaza cuentas sin confirmar, Google se auto-confirma y se vincula por email

- **Fecha:** 2026-08-18
- **Fase:** build
- **Decisión:** `POST /auth/register` ya no deja al usuario logueado — crea la cuenta con `EmailConfirmado=false` y un código de 6 dígitos (`crypto/rand`, no `math/rand`: es un secreto de un solo uso) que vence a los 15 minutos, lo manda por email, y responde `{usuario, requiereConfirmacion: true}` (sin `token`, tipo `RegisterResponse` en `shared-types`, distinto de `AuthResponse`). El frontend redirige a `/registrarse/confirmar?email=...`. `POST /auth/login` rechaza con **403** (no 401, para que el frontend lo distinga de "contraseña incorrecta") a una cuenta con `EmailConfirmado=false` — `loginAction` intercepta ese 403 puntual y redirige también a la pantalla de confirmación en vez de mostrar un error sin salida. `POST /auth/confirmar` valida el código, activa la cuenta y loguea automático (devuelve token); es **idempotente** — confirmar una cuenta ya confirmada no da error, loguea igual. `POST /auth/reenviar-codigo` siempre responde con el mismo mensaje genérico (200, exista o no exista esa cuenta, esté o no ya confirmada) — mismo criterio anti-enumeración que ya usa `login` ("mismo mensaje que password incorrecta"). Las cuentas creadas vía Google (TR-050) arrancan con `EmailConfirmado=true` directo — Google ya verificó ese email, pedir un segundo código sería fricción sin ganancia real; si el email de una cuenta de Google coincide con una cuenta ya registrada por contraseña, se **vincula** esa misma fila (`GoogleID` se setea sobre el registro existente, sin crear un duplicado) y de paso queda confirmada si no lo estaba.
- **Alternativas consideradas:** (a) Dejar `register` logueando igual que antes y solo "avisar" que hay que confirmar más tarde — se descartó: el pedido es explícito ("dejando la cuenta activada solo después de confirmar el código"), un usuario sin confirmar navegando ya autenticado contradice eso directamente. (b) Volver nullable la columna `password_hash` para las cuentas de Google (que no eligen contraseña) — se descartó a favor de generar un hash de bcrypt de un UUID aleatorio: nadie puede loguearse con contraseña para esa cuenta (nadie conoce el UUID) sin tocar una constraint `NOT NULL` que ya está en producción. (c) Para "reenviar código", devolver un error distinto si el email no existe — se descartó por la misma razón que ya documentaba `login` (no revelar qué emails están registrados).
- **Por qué:** Confirmar el email antes de dar acceso es la mitigación estándar contra altas con emails ajenos/inventados — sin esto, cualquiera puede registrar una cuenta con el email de otra persona y el "dueño" real de ese email nunca se entera. El status 403 diferenciado (en vez de forzar al frontend a parsear el texto del mensaje de error) es la forma robusta de que `loginAction` decida "mandar a confirmar" vs. "mostrar error" sin depender de que el copy del mensaje no cambie nunca.
- **Qué se sacrifica:** Un paso más entre registrarse y poder usar la cuenta (antes era inmediato) — mitigado con el login automático al confirmar y con "reenviar código" si el primer email no llega. El envío del código es best-effort (mismo criterio que la confirmación de reserva en `reservas.go`): si Resend falla, la cuenta queda creada pero sin forma de que el usuario reciba el código hasta que "reenviar código" funcione — no hay una cola de reintentos.
- **Reversibilidad:** Media — volver a loguear automático al registrarse es revertir el cambio en `register()`/`registerAction` sin tocar el modelo de datos (las columnas `email_confirmado`/`codigo_confirmacion`/`codigo_expiracion` pueden quedar sin usarse); pero cualquier cuenta ya creada sin confirmar en producción necesitaría una migración de datos aparte para no quedar bloqueada.
